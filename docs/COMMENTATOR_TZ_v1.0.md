# «Матрёшка» — мини-игра 3 «Второй комментатор»
## Техническое задание v1.0 для существующего проекта Godot / облачного Codex

**Статус:** решение на реализацию. **Приоритет:** сохранить две уже работающие мини-игры. **Платформа:** существующий Godot 4 / GDScript / браузерная сборка в GitHub Actions и GitHub Pages. **Объём:** три полностью играбельных уровня в одной новой мини-игре.

## 1. Задача

Добавить в уже существующий репозиторий мини-игру «Второй комментатор», не создавая новый Godot-проект. Игрок оказывается в будке футбольного комментатора, видит игру на поле и по очереди с основным комментатором произносит короткие футбольные фразы, которые выводятся в формате караоке. Главный вызов — **вовремя вступать и попадать в ритм каждого слова, соблюдая нужную громкость**.

**НЕ использовать распознавание речи, анализ смысла/правильности слов или оценку музыкальной высоты звука.** Анализировать лишь доступные из существующего микрофонного модуля амплитуду, моменты начала/изменения голоса, долю озвученного времени и относительную громкость. Если игрок произнесёт другое слово с нужным ритмом и громкостью, оно может засчитаться; не притворяться, что игра умеет проверять текст.

Требования исходного концепта: вид из комментаторской будки на матч, смена основного комментатора и игрока, подсветка слов как в караоке, подсказки динамики голоса, шкала интереса, три уровня с нарастанием темпа/эмоциональности. Раздел «Режим 3 / Комментатор», стр. 8, и сценарий, стр. 5 исходного документа. Текущая реализация должна соблюдать ранее принятое для всего проекта правило: всего два **типа полноэкранных сцен** (главное меню и игровые уровни); все инструкции/результаты/ошибки микрофона показываются общими **попапами поверх игровой сцены**.

- Не добавлять новых постоянных UI-панелей, графиков волн, баллов возле каждого слова, стрелок направления, кнопок записи, дополнительных индикаторов микрофона или экранов результатов. Не внедрять отдельные Scene для инструкции/результатов/выбора.

## 3. Две существующие категории экранов и сценарий переходов

1. **MAIN_MENU:** активировать карточку «Второй комментатор», не менять другие карточки. Нажатие открывает `COMMENTATOR_LEVEL`.
2. **COMMENTATOR_LEVEL:** неподвижная композиция 2.5D / 2D по исходному референсу: вид из комментаторской будки на футбольное поле; отдельные слои для фона/матча и оформления будки, временный blockout вместо финального архива.
3. Поверх COMMENTATOR_LEVEL показать уже существующий универсальный **INTRO popup** (один раз перед входом в мини-игру, не перед каждым уровнем). В нём минимум информации: «Вступай вовремя», «Следи за словами», «Усиливай выделенные слова»; кнопка «Начать». Существующую политику разрешения микрофона/ошибок и global «Сброс» сохранить.
4. Уровень начинается короткими сегментами речи основного комментатора. Пока говорит ведущий — игрок молчит, идёт уже предусмотренный оригинальным сценарием отсчёт до своего вступления. Когда начинается очередной сегмент игрока, линия караоке содержит слова с последовательной подсветкой. В конце сегмента снова очередь основного комментатора. Последовательность авторская, синхронизирована по единой временной шкале.
5. По окончании уровня показать **промежуточный popup над тем же фоном**: результат, процент попаданий в ритм, интерес, кнопки «Повторить» и «Следующий уровень» (при успешном результате); также доступно «Главное меню». При неуспехе — предложение повторить. По окончании уровня 3 — финальный popup с общим результатом трёх уровней.
6. Глобальная «Сброс» отовсюду возвращает в меню, останавливая таймеры, аудио, микрофонные подписки и Tweens текущей мини-игры. Автосброс при молчании не вводить.

## 4. Строгий минимальный состав интерфейса

Сохранить только элементы, уже заданные исходным концептом: (а) вид матча/будки; (б) минимальная подсказка, когда вступать («КОММЕНТАТОР» / «ТВОЙ ХОД», допускается обратный отсчёт); (в) **одна строка или компактный блок караоке**; (г) **одна шкала «Интерес»**; (д) существующие уровень/таймер там, где они уже приняты общей HUD-системой; (е) существующая «Сброс»; (ж) общие popup-контейнеры. Никаких самостоятельных новых постоянных UI-блоков.

### Оформление каждого слова — обязательная деталь

- В обычном слове обычная толщина шрифта, нет дополнительных знаков сверху.
- Слово, которое требуется произнести **громче**, отображается **жирным**. Непосредственно **над этим же словом** располагаются 1–2 стрелочки `↑` (светлый/контрастный вариант текущего стиля), направленные вверх. Стрелки мягко движутся вверх на несколько пикселей / слегка пульсируют, без резких вспышек. Для каждой усиленной позиции — свои стрелочки, не одна общая стрелка над строкой.
- Слова подсвечиваются **по заранее заданным таймкодам**, независимо от распознанных слов. Время слова истекло — подсветка идёт дальше даже если игрок молчал.
- Визуальная оценка успеха не требует дополнительного значка/надписи у слова: достаточно аккуратного состояния подсветки (например, пройдено / активно / ожидается) и обновления общей шкалы интереса. Не добавлять слово «ГРОМКО» или текстовую подсказку о силе над словами — только жирность и стрелочки `↑`.
- Размер, отступы, плавная подсветка, анимация стрелок и общий вход/выход попапов управляются **кодом** с редактируемыми параметрами, без предварительно рендеренной UI-анимации.

## 5. Точное поведение оценки слов и ритма

Единственный источник истины — **предварительно подготовленные временные окна слов** внутри сегмента игрока. Для каждого слова: `text`, `start_sec`, `end_sec`, `emphasis` (обычное/усиленное); все времена относительны к началу **одного** уровня и должны идти последовательно, не перекрываться. Авторские таймкоды живут в JSON/Resource и могут позже быть подогнаны под архивную запись.

- Во время сегмента основного комментатора **не начислять очки** и не анализировать громкость звука из колонок как голос игрока. По возможности приподнимать/обнулять порог голоса с учётом входного звука, но не отключать выданный доступ к микрофону между репликами; при записи ведущего, играющей из динамиков, не считать её голосом игрока.
- По каждому окну слова вычислять (на основе нормализованного живого микрофонного сигнала): присутствие голоса в ожидаемый интервал; близость момента изменения/начала голосовой активности к началу окна; характер громкости. **Слова проверяются независимо друг от друга**, даже когда реплика читается слитно.
- Не требовать полной паузы между соседними словами: обычная речь непрерывна. Для оценки начала слова использовать локальные изменения огибающей / короткие нарастания, при отсутствии явного отдельного нарастания допускать частичную оценку по активности внутри окна. Не засчитывать максимальные очки за монотонный непрерывный гул: хорошая оценка требует ритмического рисунка и для усиленных слов — повышения громкости.
- Шумовой порог калибруется автоматически через существующую систему. Для усиленного слова требуемая громкость **выше индивидуального голосового базиса**, а не абсолютный порог одинаковый для всех. Оценивать относительную динамику и сглаженную громкость; агрессивный микрофонный пик не должен давать полный балл за все слова.
- Вычислять `word_score` от 0 до 100 по комбинации времени вступления (40%), звуковой активности во временном окне (30%) и соответствия нормальной/усиленной громкости (30%). При полном отсутствии голоса — 0. При чрезмерно слабой активности ограничивать максимально доступные очки. Пороги, веса, допуски и окно сглаживания вынести в конфигурацию.
- Не путать **подсветку слова** (строго по таймкодам) и **оценку слова** (по реальному голосу). Даже неверно озвученное слово подсветится и пропустит очередь дальше.
- Реализовать «слишком рано», «вовремя», «слишком поздно» как внутренние статусы подсчёта, без новых UI-надписей. Для предотвращения двойного зачёта использовать один финализированный результат на окно; финализация происходит в `end_sec + lateness_tolerance` с защитой от наложения на соседнее слово.
- Шкала **«Интерес»** — единый обратный отклик игроку, 0–100. Начальное значение и скорость изменения настраиваемы: успешные слова повышают, пропущенные/плохие понижают; во время речи ведущего шкала остаётся стабильной. Плавность изменения шкалы задаётся кодовой Tween-анимацией. Статистика уровня фиксирует процент выполненных слов и средний `word_score`.

## 6. Три полноценные уровня сейчас

**Каждый уровень должен иметь весь цикл:** сценарий ведущего/игрока, несколько сегментов игрока, пословные таймкоды, оценку, конец уровня, возможность повторить, переход на следующий, корректный сброс. Это НЕ заготовки/отключённые уровни. По умолчанию длительность каждого — около **60 секунд** (в исходном сценарии диапазон 1–2 минуты). Допускается 55–65 секунд, если это нужно для корректного завершения целой реплики; окончательная длительность — значение из конфигурации.

| Параметр | Уровень 1 | Уровень 2 | Уровень 3 |
|---|---|---|---|
| Темп караоке | спокойный | быстрее | быстрый |
| Среднее окно слова | примерно 0,65–0,85 с | 0,50–0,70 с | 0,38–0,55 с |
| Время предупреждения о ходе | 2,0 с | 1,5 с | 1,0 с |
| Акцентные слова | 1–2 на фразу | 2–3 на фразу | 3–4 на фразу |
| Допуск начала | ±0,35 с | ±0,25 с | ±0,18 с |
| Порог прохода (средний балл) | 50/100 | 60/100 | 65/100 |
| Штраф интереса при пропуске | мягкий | средний | заметный |

**Таблица — стартовые параметры баланса**, не физическая достоверность и не утверждённые автором архивные таймкоды. Все числа сделать настраиваемыми; не требовать невозможных 1:1 попаданий в реальные слова для успешного прохождения. В каждом уровне должны быть разные короткие футбольные реплики и меняющийся характер интонации, а не три раза одна и та же строка с ускоренной анимацией.

Результат каждого уровня: `words_hit`, `words_total`, `avg_word_score`, `interest_end`, `pass/fail`. Успех определяется средним баллом не ниже целевого для уровня (интерес — визуальная обратная связь, не скрытое второе условие, если дизайнер не утвердил иное). Общий финал уровня 3 показывает суммарный процент, результат по каждому уровню и предлагает повтор или возврат в меню, через общий popup.

## 7. Подготовка данных и материалов: строго честный демонстрационный режим

**Архивных файлов и подтверждённых прав пользователь для этой задачи не предоставил.** Следовательно:

- Создать **три полноценных демонстрационных сценария** (по одному на уровень) с вымышленными футбольными событиями без дат, ФИО великих комментаторов, названий реальных матчей или утверждений об исторической подлинности. Они нужны для проверки караоке. Они не являются архивом.
- В каждом уровне не менее 5 чередований ведущего и игрока и достаточное число слов игрока для работы всех трёх уровней. Создать все пословные таймкоды; сценарий должен укладываться в установленный таймер, не обрезая фраз.
- Несколько примерных пар реплик, которые можно расширить в конфигурациях (НЕ приписывать реальному комментатору):
  - Уровень 1: ведущий «Команда начинает атаку…», игрок «ПЕРЕДАЧА на фланг!», акцент «ПЕРЕДАЧА»;
  - Уровень 1: ведущий «Мяч уже у штрафной…», игрок «УДАР по воротам!», акцент «УДАР»;
  - Уровень 2: ведущий «Опасный прорыв по центру…», игрок «БЫСТРАЯ передача — ОСТРЫЙ момент!», акценты «БЫСТРАЯ», «ОСТРЫЙ»;
  - Уровень 3: ведущий «Секунды до развязки…», игрок «МОЩНЫЙ УДАР! НЕВЕРОЯТНЫЙ ГОЛ!», акценты «МОЩНЫЙ», «УДАР», «ГОЛ».
- Весь текст вне GDScript. Редактируемые данные: `commentator.ui.ru.json` (фразы интерфейса, инструкция, короткие итоги) и `commentator.levels.json` (ведущий/игрок, абсолютные таймкоды слов, акценты, пути аудио и видео). Значения баланса отдельно в `commentator.gameplay.json`, программные анимации — в `commentator.animations.json` или расширениях существующих конфигов по принятой в репозитории схеме. Не плодить новые конфигурационные системы, если текущая уже поддерживает расширение.
- **Архивные ролики и голос ведущего** должны подключаться как заменяемые медиа по путям из конфигурации. Если подходящего аудио нет, сцена всё равно полностью играбельна на демонстрационных данных: ходы ведущего показываются тем же блоком текста без обязательной озвучки; последовательность и тайминг не зависят от наличия медиа. Если существует безопасный локальный механизм создания временной озвучки, допускается использовать, но он не должен вводить сетевые зависимости, ломать Web export или выдавать себя за исторический архив. Не придумывать ссылки на несуществующие архивы.
- Демонстрационную графику поля и будки создать примитивами/плейсхолдерами, ориентируясь на композицию со стр. 8 исходного концепта. Не создавать через код новые самодельные UI-панели за пределами согласованного состава. Заложить slots для замены демонстрационного фона, архивного видео, голоса ведущего и портретов без смены игровой логики.
- Выбор нескольких исторических матчей из исходного документа зависит от предоставленных архивов и метаданных: в текущем прототипе **один демонстрационный сюжет на три уровня без ложных исторических карточек**; когда появятся проверенные архивные материалы — появится возможность выбора матчей в существующем intro popup, но это не отдельная сцена и не блокирует текущую работу.

### Минимальный контракт уровня (схематичный, не исчерпывающий)

```json
{
  "id": 1,
  "duration_sec": 60,
  "pass_avg_score": 50,
  "turns": [
    {"speaker":"host", "start_sec":0, "end_sec":5, "text":"Команда начинает атаку...", "audio_path":""},
    {"speaker":"player", "start_sec":5, "end_sec":9, "words":[
      {"text":"ПЕРЕДАЧА", "start_sec":5.0, "end_sec":6.0, "emphasis":true},
      {"text":"на", "start_sec":6.0, "end_sec":6.6, "emphasis":false},
      {"text":"фланг!", "start_sec":6.6, "end_sec":7.6, "emphasis":false}
    ]}
  ]
}
```

**Это только пример структуры.** Полные файлы уровней должны содержать авторский сценарий и валидные интервалы на протяжении всех ~60 секунд для каждого из трёх уровней. Проверить, что в JSON нет пересечения слов/ходов, отрицательных интервалов, дыр в таймере без авторского решения, обрезанных сегментов или недостижимых результатов.

## 8. Техническая реализация в существующем Godot

1. Перед кодом изучить актуальные `AGENTS.md`, `project.godot`, имеющиеся `scenes/`, `scripts/`, `data/config/`, WebAudio bridge, слои popups, input manager, анимационные контроллеры, меню и GitHub workflow. Пути в этом ТЗ — логические, а не требование поменять существующую структуру.
2. Добавить полноценную игровую сцену `CommentatorLevel` (название по конвенциям проекта), модуль `commentator_session`, `commentator_timeline`, `commentator_word_scorer`, рендерер караоке и слой заменяемого медиа; интегрировать с уже работающими навигацией, микрофоном, конфигами, локализацией и общими popup.
3. Для подсчёта отделить: `timeline clock` (монотонный `level_time`) → расписание ходов → расписание слов → `microphone samples` → `word_score` → `interest` → `level_result`. Когда открывается popup, clock и scoring стоят; после reset ни один отложенный callback не должен менять новую сцену.
4. Из WebAudio для микрофона брать нормализованную энергию/RMS через существующий сервис. Если для оценки ритмических нарастаний нужны новые поля, расширить интерфейс обратносовместимо без изменения контракта первых двух игр.
5. Медиаплеер по возможности работает локально с конфигурационными путями и синхронизирован по clock; при отсутствии медиа — без ошибки. Громкость воспроизводимого голоса основного комментатора не засчитывать игроку; `speaker=host` полностью блокирует начисление очков. Для web-браузера учитывать ограничения autoplay и разрешения аудио после клика «Начать».
6. При управлении из Codex не требовать постоянно подключённый физический микрофон: предоставить отдельный DEBUG-источник виртуальной громкости/ритмического сигнала, не открытый публичному пользователю. Через него запускать автоматические тесты. Реальная браузерная проверка микрофона будет необходима отдельно после публикации.
7. Пользовательские тексты и анимации UI НЕ хардкодить в GDScript, использовать существующие JSON и кодовые Tweens, с параметрами для подчёркивания активного слова и мягких стрелок над акцентами.
8. При показе попапов не должно быть изменения полноэкранной сцены. Фоновые декоративные анимации могут продолжаться, но оценивающая механика на паузе.

## 9. Критерии приёмки

- [ ] Обе ранее работающие мини-игры запускаются и работают по-прежнему.
- [ ] Карточка «Второй комментатор» активна и ведёт к третьей мини-игре; global «Сброс» работает везде.
- [ ] Существующий popup инструкции появляется только один раз перед мини-игрой; после уровней — те же общие промежуточные/финальные popup.
- [ ] Реализованы **все три** уровня, с собственными сценариями, таймкодами, переходами, повторами и результатами.
- [ ] Ведущий и игрок чередуются; звук/голос игрока не оценивается в ход ведущего.
- [ ] Слова подсвечиваются последовательно строго по таймкодам без ожидания результатов STT.
- [ ] Усиленные слова **жирные**, над **каждым** есть легкие анимированные стрелки `↑`; обычные слова без стрелок.
- [ ] Оцениваются тайминг и динамика каждого слова, включая ритмическое изменение громкости; непрерывный гул не даёт максимум очков.
- [ ] Никакого распознавания текста, произнесённых слов и музыкального pitch tracking нет.
- [ ] Шкала интереса плавно обновляется и соответствует качеству слова; результат уровня повторяем при одинаковом DEBUG-вводе.
- [ ] Медиа можно подменить через конфигурацию; при отсутствии исторических материалов демо-игра работает.
- [ ] Все UI-тексты и параметры программных анимаций редактируются отдельно от кода.
- [ ] Нет лишних постоянных UI-деталей сверх описанного набора.
- [ ] Есть тесты на 0-сигнал, идеальный ритм, ранний/поздний вход, слабое акцентное слово, громкий акцент, непрерывный гул, сброс посреди реплики, переходы между всеми уровнями и запрет начисления в `host` turn.
- [ ] Godot headless import и Web export проходят; GitHub Actions workflow сохранён. Codex сообщает, что проверено автоматически, и что требует реального браузера/микрофона.

## 10. Порядок работ Codex

Аудит репозитория → расширение конфигураций/данных (три полностью размеченных уровня) → модуль timeline/scorer и его тесты → сцена/минимальный UI → интеграция звука и заменяемого видео → меню/попапы/переходы → тесты регрессии первых двух игр → Web export/CI → pull request/отчёт. Если код первой/второй игры связан теснее ожидаемого, минимально расширить общие абстракции, не переписывая поведение. Не запрашивать у пользователя исторические архивы для запуска демо. Отчёт должен перечислить созданные файлы, выполненные проверки и ограничения демо-медиа.
